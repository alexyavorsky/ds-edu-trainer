# План справочника «Git» (поток С3)

Справочник по Git для того, кто работает один или в небольшой команде: основы и раздел «Проблемы и как их
решить». Каждый пример — shell-скрипт, который валидатор выполняет во временной папке настоящим git и
сохраняет реальный вывод. В браузере примеры не выполняются: на сайте — «команда → вывод».

Тема: `reference/git/`, URL `/reference/git/<статья>`, id `git/<статья>`. Направление на сайте — «Git».

## Объём

**30 статей** (основы 17 · проблемы 12 · шпаргалка 1), ≈ 150 примеров (4–6 на статью), статья — 60–160 строк MDX.
Уровни: **Б** — базовый, **С** — средний, **П** — продвинутый.

| `remotes` Удалённые репозитории | С | `remote add` / `-v` / `rename`, `origin`, удалённые отслеживаемые ветки `origin/main`, upstream (`-u`, `branch -vv`), ahead / behind |
| `fetch-pull-push` fetch, pull, push | С | fetch не меняет ваши ветки; pull = fetch + merge или rebase; `pull.rebase`, `pull.ff only`; push новой ветки, удаление удалённой ветки; `git push` без аргументов |
| `tags` Метки | Б | лёгкие и аннотированные метки, `tag -a`, `push --tags` / одной метки, `describe` |

### 2. Проблемы и как их решить

Структура статьи: «Коротко» → «Симптом» (что видите, реальный вывод) → «Почему так» → «Решение» (по шагам,
варианты) → «Примеры» → «Подводные камни» (в т. ч. «как не допустить»).

| Статья | Ур. | Содержание |
| --- | --- | --- |
| `diverged` Разошлись локальная и удалённая ветки | С | `Your branch and 'origin/main' have diverged`; подсказка git о `pull.rebase`; три пути — merge, rebase, `--ff-only` + ручное решение; как посмотреть расхождение (`log --oneline main...origin/main`, `rev-list --left-right --count`) |
| `extra-merges` pull без rebase: лишние merge-коммиты | С | откуда «Merge branch 'main' of …», как выглядит граф; `pull --rebase`, `pull.rebase true`, `rebase.autoStash`; как убрать уже созданный merge-коммит, пока не отправлен (`reset --hard ORIG_HEAD` / rebase) |
| `push-rejected` Отклонённый push | С | `! [rejected] … (fetch first)` и `(non-fast-forward)`; правильный порядок fetch → rebase/merge → push; почему не `--force`; отказ из-за защищённой ветки — только текстом |
| `conflicts` Конфликты | С | маркеры `<<<<<<<` / `=======` / `>>>>>>>`, `git status` при конфликте, решение и `add` + `commit` / `rebase --continue`, `--abort`, `checkout --ours/--theirs`, `merge.conflictStyle zdiff3`; конфликт при rebase — по коммиту за раз |
| `undo-commit` Отменить коммит: reset, revert, amend | С | таблица «что случилось → команда»: поправить последний (`--amend`), убрать неотправленные (`reset --soft` / `--mixed` / `--hard` — что с файлами), отменить отправленный (`revert`, в т. ч. merge-коммита `-m 1`); схема движения указателей |
| `wrong-branch` Коммит не в ту ветку | С | сделали в `main` вместо фичи: `branch` + `reset`; в чужую ветку: `cherry-pick` + `reset`; если уже отправили — `revert` |
| `detached-head` Отделённый HEAD | С | как попадают (`checkout <хеш>`, метка, rebase с конфликтом), что пишет git, как сохранить коммиты (`switch -c`), как вернуться |
| `reflog` Потерянный коммит и reflog | П | `git reflog`, `HEAD@{n}`, восстановление после `reset --hard`, удалённой ветки, неудачного rebase (`ORIG_HEAD`); сколько живёт reflog; `fsck --lost-found` одним абзацем |
| `stash` Отложить изменения: stash | С | `stash push -m`, `-u`, `list`, `show -p`, `apply` против `pop`, конфликт при `pop`, `stash branch`; альтернатива — временный коммит |
| `untrack-file` Файл закоммичен, а должен игнорироваться | С | `.gitignore` не действует на отслеживаемые файлы; `git rm --cached`, папка `-r`; что станет у коллег при pull (файл удалится!) и как этого избежать |
| `force-push` force push и --force-with-lease | П | когда нужен (после rebase своей ветки), чем опасен `--force` (затирает чужие коммиты — пример), `--force-with-lease` отказывает, если удалённая ветка сдвинулась, и его ловушка с `fetch`; `--force-if-includes` |
| `leaked-secret` Закоммитили секрет | П | порядок: **сначала отозвать ключ**, потом чистить; не отправлен — `--amend` / `rebase -i`; отправлен — переписать историю (`git filter-repo` — внешняя утилита, пример `[norun]`), force push, почему этого недостаточно (форки, кэши); как не допустить: `.env` в `.gitignore`, pre-commit; в примерах только заведомо поддельные значения вида `API_KEY=not-a-real-key` (реалистичный токен заблокирует push protection GitHub) |

## Формат примеров

Файлы: `reference/git/<статья>.mdx` + `<статья>.sh` (ячейки `# %% id [флаги]`, вывод под `# ─── вывод ───`
пишет валидатор — как в `.py`). Пример:

```bash
# %% setup
git init -q shop && cd shop
echo "кофе" > menu.txt && git add menu.txt && git commit -qm "Меню"

# %% amend
echo "чай" >> menu.txt
git commit -am "Добавил чай"
git commit --amend -m "Меню: добавил чай"
git log --oneline
# ─── вывод ───
# $ git commit -am "Добавил чай"
# [main 1c2d3e4] Добавил чай
#  1 file changed, 1 insertion(+)
# $ git commit --amend -m "Меню: добавил чай"
# ...
```

- **Ячейка = скрипт**: prelude → setup → код ячейки, каждый пример — с нуля в своей временной папке (как в
  справочнике Python: пример независим, «Копировать» даёт самодостаточный скрипт).
- **Вывод по командам.** Валидатор выполняет ячейку в одном процессе `bash` построчно: каждая полная команда
  верхнего уровня (многострочную — `if`, heredoc — собирает, пока `bash -n` не примет) печатается строкой
  `$ команда`, под ней — её stdout и stderr вперемешку в порядке появления (`2>&1`) и, если не 0, код возврата.
  На сайте строки `$ …` — команды (подсвечены, копируются), остальное — вывод.
- **Команды, которые должны завершиться ошибкой** (отклонённый push, конфликт merge): флаг ячейки `[fails]`;
  без него ненулевой код любой команды — ошибка валидатора. Скрытые служебные строки (подготовка «коллеги»
  в другом клоне) — только в `setup`, он показывается свёрнутым блоком, как `<Setup />`.
- **Редактор.** `GIT_EDITOR=false` в prelude: команда, случайно открывшая редактор, падает сразу. Сообщения —
  через `-m`, слияния — `--no-edit`. Для `rebase -i` пример задаёт список действий явно:
  `GIT_SEQUENCE_EDITOR="sed -i.bak '2s/^pick/fixup/'" git rebase -i HEAD~3` (`-i.bak` работает и в GNU, и в
  BSD sed), а текст статьи объясняет, что в жизни откроется редактор, и показывает список `cat`-ом.
- **Интерактивное** (`add -p`, `mergetool`) — флаг `[norun]`: только синтаксис, без вывода.

## Детерминизм

Проверено на git 2.54: с настройками ниже два прогона дают одинаковые хеши и вывод, различаются только пути
временной папки (их заменяет валидатор).

| Что | Как |
| --- | --- |
| хеши коммитов | автор и коммиттер фиксированы (`GIT_AUTHOR_NAME/EMAIL`, `GIT_COMMITTER_NAME/EMAIL`); дата — в prelude функция-обёртка `git()`, которая перед каждым вызовом прибавляет 60 с к счётчику и передаёт `GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE="@<секунды> +0300"`: хеши стабильны, даты в `log` растут реалистично, в тексте примера — обычные `git …`; `TZ=UTC` |
| формат объектов | `GIT_DEFAULT_HASH=sha1` (на случай git 3.0, где по умолчанию может стать sha256) |
| длина хеша | `core.abbrev=7` (иначе длина растёт с числом объектов) |
| конфигурация | `HOME` = временная папка, `GIT_CONFIG_NOSYSTEM=1`, свой `~/.gitconfig` из prelude: `init.defaultBranch=main`, `core.autocrlf=false`, `color.ui=never`, `core.pager=cat`, `pull.rebase` **не задан** (иначе не показать подсказку о расхождении), `advice.*` — по умолчанию: подсказки git — часть того, что видит человек, их и объясняем |
| окружение | `LC_ALL=C LANG=C` — вывод на английском (переводы git на машинах разные; в тексте статьи — перевод и разбор), `GIT_PAGER=cat`, `PAGER=cat`, `TERM=dumb`, `umask 022`, без `GIT_*` из окружения разработчика (валидатор запускает `env -i` + белый список) |
| пути | «удалённый» репозиторий — `git init --bare server.git` во временной папке, клоны — рядом (`me/`, `colleague/`); git печатает абсолютные пути (`To /var/…/server.git`) — валидатор заменяет корень временной папки (и его `realpath`: на macOS `/var` → `/private/var`) на `/work` |
| прогресс | вывод не в терминал — прогресс-бары push/clone не печатаются; при необходимости `--quiet` |
| версия git | фиксируется в `topic.toml` (`version = "2.54.0"`); валидатор сверяет `git --version` по major.minor и при несовпадении не сравнивает вывод (как справочник Python при других версиях пакетов). В CI git собирается из исходников тега `v2.54.0` с кэшем (см. «Нужно от платформы»). Apple Git на macOS (`2.54.0 (Apple Git-157)`) проходит сверку; различия, если найдутся, — повод запускать валидатор в Docker |
| оболочка | `bash`, без возможностей bash 4+ (на macOS bash 3.2); `set -o pipefail` не включаем — код возврата каждой команды проверяет валидатор |

## Показ на сайте

- `<Example id title />` в статье темы git рендерит терминальный блок: `$ команда` (подсветка shell),
  вывод серым моноширинным, код возврата ≠ 0 — пометкой «ошибка: код 1». Кнопки «Запустить» нет, в шапке
  статьи — «Git 2.54», а не версия пакета.
- «Копировать» копирует только команды (setup + ячейка) без вывода, с первой строкой-комментарием
  «выполнять в пустой папке» и `mkdir demo && cd demo`; prelude (обёртка дат) не копируется.
- Схемы: граф коммитов — выводом `git log --oneline --graph --all`; компонент `CommitGraph` нужен только для
  трёх статей (`intro`, `rebase`, `undo-commit`) — схема «до → после» указателей. Предлагаю сделать его в
  платформе, если ревью первой трети подтвердит, что текстового графа мало.

## Проверка

- `python3 scripts/validate_git.py [статья] [--update] [--strict]` (новый, см. ниже) — структура статей, ссылки,
  все ячейки выполняются, вывод совпадает; `--strict` — все статьи оглавления написаны.
- Прогон дважды подряд даёт тот же вывод (детерминизм) — делает сам валидатор с `--check-determinism` в CI.
- Ревью: каждый «рецепт» из «Проблем» воспроизводит симптом реальным выводом и показывает, что после решения
  `git status` / `log --graph` в ожидаемом состоянии.

## Критерии готовности

- 30 статей (не меньше 28), валидатор зелёный локально и в CI, вывод всех примеров — реальный, руками не правлен.
- Каждая статья «Проблем» содержит пример-симптом (с `[fails]`, где git отвечает ошибкой) и пример-решение.
- Никаких реалистичных секретов в репозитории; `leaked-secret` проходит push protection GitHub.
- Шпаргалка ссылается только на существующие статьи; поиск находит по командам (`functions: [git rebase, …]`).

## Нужно от платформы

1. **Тема без Python и без пакета**: `topic.toml` без `package`, с `version` = версия git и новым полем
   `runtime = "shell"` (или `language = "bash"`); схема `src/content.config.ts`, `validate_reference.py` не
   трогает такую тему (или делегирует `validate_git.py`).
2. **Валидатор `scripts/validate_git.py`** (стандартная библиотека Python): разбор `.sh` на ячейки и флаги
   (`[fails]`, `[norun]`), prelude `reference/git/prelude.sh` (окружение из таблицы «Детерминизм»), выполнение
   по командам в `bash` с маркерами между командами, замена путей временной папки на `/work`, запись вывода
   (`--update`), сравнение, проверка структуры и ссылок MDX (общий код с `validate_reference.py`), сверка версии
   git с `topic.toml`, `--check-determinism` (два прогона).
3. **Компонент показа**: `<Example>` для темы с `runtime = "shell"` читает `.sh` и рендерит «команда → вывод»
   без кнопки «Запустить»; подсветка shell в Shiki; «Копировать» — только команды; шапка — «Git 2.54».
   Воркер Pyodide на страницах темы не создаётся.
4. **Поиск**: `.sh`-примеры и `functions` (команды git) в индексе `/reference/search.json`.
5. **CI**: задание «Справочник Git» на ubuntu: собрать git `v<version>` из исходников
   (`make prefix=$HOME/git install`, зависимости `libcurl4-openssl-dev libexpat1-dev gettext zlib1g-dev
   libssl-dev`), кэш `actions/cache` по версии, `PATH` на собранный git, затем `validate_git.py --strict
   --check-determinism`. Python-пакеты не нужны. (Альтернатива — контейнер с нужной версией git, если найдётся
   официальный образ с точной версией.)
6. **Навигация и «бета»** — общие: `direction = "git"`, `beta = true` (описаны в `docs/ALGORITHMS_PLAN.md`,
   «Нужно от платформы», п. 5–6).
7. **Компонент `CommitGraph`** (необязательно, после ревью первой трети): схема коммитов и указателей
   «до → после» из небольшого описания в MDX.

## Открытые вопросы (исходная формулировка)

- Вывод git на английском (`LC_ALL=C`) — предлагаю так: русский перевод git неполон и зависит от пакета
  `gettext`; в статьях — перевод ключевых строк. Если нужен русский вывод — придётся фиксировать и локаль в CI.
- Версия git: 2.54.0 (как у разработчика) или последняя на дату старта потока — решить при старте С3.
- Нужен ли раздел про GitHub (PR, форки, SSH-ключи)? Предлагаю нет: только git; SSH и HTTPS-токены — одним
  абзацем в `remotes`.
