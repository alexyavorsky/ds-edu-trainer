## Главы: своё деление, а не разделы справочника

Сейчас `book.toml` обещает «Разделы — как в справочнике». **Решение: главы по видам задач** (4 на тему),
связь со справочником — через `refs` у каждой задачи. Почему: прикладная задача задействует 3–4 раздела
справочника сразу (кадрирование — индексация, форма, pad), и при делении «как в справочнике» получились бы
главы по 1–2 задачи при требовании валидатора 6–10. Страница темы по-прежнему ведёт в справочник (`reference`
в `book.toml` остаётся). Нужна правка описаний в `book.toml` (делают З1/З2) и строки в `ARCHITECTURE.md`
«главы темы повторяют её разделы» (платформа).

Уровни: **Л** — easy, **С** — medium, **Т** — hard. Тип: `impl` · `fix` · `compl` · `cx` (complexity).
«Справочник» — `refs` (без префикса темы для краткости: у NumPy — `numpy/…`, у pandas — `pandas/…`),
«Курс» — уроки курса той же темы (новое поле `lessons`, см. «Нужно от платформы»).

## Данные в задачах

Задача копируется одним файлом, поэтому данные — внутри файла.

1. **Функция принимает данные аргументом** (массив / DataFrame) и возвращает результат — никаких чтений
   файлов в решении. Для задач «прочитать CSV» аргумент — текст CSV (`str`), решение читает
   `pd.read_csv(io.StringIO(text))`: так моделируются «грязные» выгрузки с кавычками и пробелами.
2. **Маленькие таблицы (5–20 строк) — литералами** в `tests.py`: словарь столбцов или CSV-текст в тройных
   кавычках; ожидаемый ответ — тоже литерал. Это основа тестов на правила и граничные случаи.
3. **Большие данные — генератором** на `random.Random(seed)` (стандартная библиотека: последовательность
   стабильна между версиями Python и совпадает в Pyodide), а не `np.random`: поток `Generator` в NumPy 2.4
   (Pyodide) и 2.5.3 (CPython) не обязан совпадать. Проверки — заранее посчитанные эталоном числа-литералы
   (итоги, число строк, контрольные суммы) и инварианты (сумма долей = 100 %, строки не потеряны).
   Генератор — вспомогательная функция данных, он не решает задачу, так что правило «в тестах нет функций,
   решающих задачу» не нарушается.
4. **Где живёт код данных.** Предлагаю новый необязательный файл задачи **`data.py`**: функции вроде
   `sample_orders()` и `make_orders(n, seed)`; в копируемом файле — отдельный блок «Данные» **перед**
   заготовкой, так что человек может вызвать `sample_orders()` в своём коде и посмотреть на данные, а тесты —
   использовать их. Лимит — 150 строк; сами данные строятся кодом, не хранятся таблицей. До появления
   поддержки в платформе (или если её не будет) генераторы живут в `tests.py` — это работает уже сейчас, но
   данные тогда видны только в тестах и примерах `task.md`.
5. **Изображения для NumPy** — синтетические, строятся кодом: градиент, круги, шахматная доска, шум с
   `random.Random` → `np.array`. Размеры тестов ≤ 200×200 (Pyodide), в «Примерах» `task.md` — массив 4×4.
6. Размер данных: ≤ 2·10⁴ строк / 10⁶ элементов в обычных тестах, чтобы тест укладывался в 2 с на CPython и
   в лимит ×3 в браузере с запасом.

## Правила тестов (дополнение к «Приёмам в тестах»)

- **Разрядность** (Pyodide 32-битный): значения, не dtype — `np.array_equal`, `.tolist()`,
  `pd.testing.assert_frame_equal(..., check_dtype=False)`; dtype проверяется только в задачах про тип
  (`np-grayscale` — `uint8`, это не зависит от платформы), и тогда `np.issubdtype`, не `==` с `int64`.
- **float** — `math.isclose` / `np.allclose` / `assert_frame_equal(rtol=…)`; никаких сравнений repr.
- **pandas 3**: строковый dtype (`str`) в Pyodide может быть с другим хранилищем (без pyarrow) — dtype строк не
  сравнивается; единица `datetime64` (s / us / ns) выводится из данных — даты сравниваются значениями
  (`.tolist()` Timestamp'ов), а не dtype; порядок групп — всегда явная сортировка.
- **Случайность**: решение получает `rng` (или `seed`) аргументом; тесты не сравнивают конкретные случайные
  значения NumPy — только свойства (форма, диапазон, сумма, воспроизводимость при одном seed, статистика с
  допуском на большом n с фиксированным seed и 5σ запасом).
- **Векторизация** не проверяется тестами (как запреты `sorted` в книге) — только в условии. Тест
  производительности — лишь там, где наивный цикл медленнее в ≥ 20 раз (матрица расстояний, свёртка, сессии),
  с лимитом и понятным сообщением «похоже, цикл по строкам — используйте …». Подкласс `ndarray`, считающий
  итерации, отвергнут: `np.asarray` в решении снимает подкласс.
- **Предупреждения**: эталон не выдаёт `FutureWarning` / `DeprecationWarning` / `SettingWithCopyWarning`
  (pandas 3 с Copy-on-Write) — проверяет валидатор (см. «Нужно от платформы»); в тестах предупреждения о
  делении на ноль не проверяются (их нет в WebAssembly).
- **Версии**: только API, которое есть и в Pyodide (NumPy 2.4.x, pandas 3.0.x), и в `requirements-dev.txt`
  (NumPy 2.5.3, pandas 3.0.6) — как в курсах.
- **`mutants.toml`** — у каждой `implement` ≥ 2 типичные ошибки (например, `axis=0` вместо `axis=1`, `how="inner"`
  вместо `left`, `shift(7)` вместо `shift(freq="7D")`); **`alt_solutions/`** — версия с циклом там, где она
  корректна (должна проходить тесты, если не тест производительности).

## Нужно от платформы

1. **`data.py` в задаче** (необязательный): валидатор (`scripts/validate.py` — набор файлов, компиляция,
   импорты только stdlib + `packages`, сборка) и `src/lib/bundle.ts` — блок «# ════ Данные» между docstring
   и заготовкой; на сайте — в редакторе он не редактируется, показывается свёрнутым блоком «Данные задачи»
   над редактором (или вставляется в footer до заготовки — решить при реализации); `check:bundles` сверяет.
2. **Поле `lessons` в `meta.toml`**: список `курс/урок` (`numpy/broadcasting`); валидатор проверяет, что урок
   существует; страница задачи показывает «Урок курса» рядом со «Справочником».
3. **Блок «Задачи по теме» в статье справочника** — по обратным `refs` (при сборке).
4. **Docstring копируемого файла** у задач темы — строка «Нужно: numpy (проверено на 2.5.3)» из `packages` и
   `requirements-dev.txt`, чтобы файл, запущенный без пакета, было понятно чем чинить (и понятное сообщение
   раннера при `ImportError`).
5. **Предупреждения в эталонах**: `validate.py` запускает эталон с `-W error::FutureWarning
   -W error::DeprecationWarning` (и `pandas.errors.SettingWithCopyWarning`) для задач тем.
6. **Правка документации**: `ARCHITECTURE.md` — «главы темы — свои, по видам задач; связь — `refs`»; «скоро»
   на карточках снимается автоматически, когда в теме есть главы (уже так).
7. **CI** (`.github/workflows/tasks.yml`):
   - задание «Валидация задач» ставит `requirements-dev.txt` (сейчас задачи — только stdlib);
   - матрица файлов задач: задачи тем — на Python 3.12–3.14 × три ОС с `pip install numpy==2.5.3
     pandas==3.0.6` (если колёс для 3.10/3.11 нет — `run_bundles.py` пропускает файл, чьи `packages` не
     импортируются, с пометкой «пропущено: нет numpy», а книги по-прежнему идут на 3.10–3.14);
   - Pyodide: кэш пакетов уже есть (NumPy, pandas); время задания вырастет на ~54 задачи;
   - браузеры (`validate_browsers.ts`): задачи тем — только Chromium, чтобы не утроить время загрузки pandas
     (глубина рекурсии для них не проверяется — рекурсии нет).
8. **Навигация и «бета»** — общие для всех потоков (`direction = "data"`, `beta = true`), см.
   `docs/ALGORITHMS_PLAN.md`, «Нужно от платформы», п. 5–6.

## Открытые вопросы (исходная формулировка)

- `data.py` или генераторы в `tests.py`? Предлагаю `data.py` — человек видит и может потрогать данные до
  тестов. Если платформа не успевает к старту З2 — первая треть пишется с генераторами в `tests.py`, потом
  переносится (механически).

  вопросы про O(·).
- Нужны ли графики в задачах (например, «постройте гистограмму»)? Предлагаю нет: проверять нечего, кроме
  данных под графиком — их и проверяем.
