## Причина падений WebKit

Коротко: **ошибка JavaScriptCore в WebAssembly, которая проявляется на виртуальных машинах macOS arm64 в GitHub
Actions** — примерно один сбой на 600–1500 запусков Pyodide. Не память и не «сотни воркеров в одной странице».
Нашим кодом её не убрать; теперь она стоит повтора одной пачки, задачи или запуска Python, а не всего прогона, и
каждый такой повтор виден. Подробный разбор — docs/ARCHITECTURE.md, «CI».

Как искал:

1. Журнал старой проверки терялся при падении страницы. Сделал журнал по мере выполнения (console страницы и
   воркеров) и временный workflow `diag-webkit`: 5 параллельных прогонов WebKit по старой схеме со снимками памяти,
   журналом ядра и отчётами о сбоях `.ips`. Воспроизвёл: 3 падения из 9 прогонов (как в CI).
2. **Память — нет:** в момент падения у процесса WebContent 200–600 МБ, у машины 80 % памяти свободно.
3. Отчёты о сбоях: `EXC_BAD_ACCESS`/`SIGBUS` в потоке «WebCore: Worker», ядро — «Data/Stack execution not permitted»:
   JIT-код перешёл на адрес в куче. Первая гипотеза — «порча накапливается от воркера к воркеру» (падало на воркерах
   №87–149) — сделал пачки по 25 в новых контекстах (у WebKit это новый процесс).
4. **Гипотеза не подтвердилась.** В 16 полных проходах WebKit по новой схеме — 3 сбоя (два «Out of bounds memory
   access» при запуске Python, одно падение вкладки на 7-м воркере свежего процесса): та же частота на запуск.
5. Стресс-тест (только запуск Pyodide, `scripts/stress_webkit.ts`) на CI, пачки по 25:

   | Вариант (macos-latest, arm64, ВМ) | Запусков | Сбоев | На запуск |
   | --- | --- | --- | --- |
   | 3 вкладки (2 задания) | 3078 | 5 | 0,16 % |
   | 3 вкладки, пауза 3 с перед `terminate()` (2 задания) | 1802 | 3 | 0,17 % |
   | 1 вкладка | 1401 | 1 | 0,07 % |
   | Mac M-серии, настоящее железо, 6 вкладок по 500 запусков | 3000 | 0 | 0 % |

   Сбои — на 1-м, 5-м, 21-м воркере свежего процесса (не накопление), пауза перед `terminate()` не влияет.
   Отчёты о сбоях (12 штук, все — поток «WebCore: Worker», JavaScriptCore): 5 × `EXC_BREAKPOINT` (проверка движка;
   3 из них — в `JSC::StackVisitor::readInlinableNativeCalleeFrame` при создании ошибки WebAssembly), 5 ×
   `EXC_BAD_ACCESS` (адрес 0, мусорный адрес, исполнение памяти без права исполнения), 2 × `EXC_BAD_INSTRUCTION`.
6. Проверка расчётом: полная проверка WebKit — ~230 запусков Pyodide; при 0,16 % хотя бы один сбой в
   1 − 0,9984^230 ≈ 31 % прогонов — ровно та частота, с которой падал main.

Что сделано:

- пачки по 25 в новом контексте и вкладки параллельно — падение процесса стоит повтора ≤ 25 задач и уроков;
- повтор **только** сбоев среды, один раз: упавшая вкладка — пачка; задача или урок со статусом сбоя движка
  (`crash`, «fatally failed», ловушка WebAssembly) — эта задача или урок; обязательная проба глубины с аварийным
  итогом — эта проба; запуск Python — до двух повторов. Провал тестов, расхождение вывода и таймауты не
  повторяются; детерминированное падение повторяется и остаётся ошибкой (проверено имитацией);
- каждый повтор — строка в журнале, `::warning`, строка «Повторов: N» и таблица в сводке задания.

Что не сделано и почему: отключить в WebKit оптимизирующий компилятор WebAssembly или сменить раннер на Intel —
это изменило бы то, что проверяется (бюджет глубины рекурсии меряется на arm64, как у Safari на Mac и iPhone).
Раннеры macOS без виртуализации у GitHub бесплатно недоступны.

Повторы, по правилу задания, нужны регулярно — примерно в каждом третьем полном прогоне. Причина при этом найдена:
она вне нашего кода. Предлагаю сообщить в WebKit (bugs.webkit.org) с отчётами о сбоях из артефактов `diag-webkit`;
сам я этого не делал — это внешнее действие от вашего имени.

## Плавающий пример справочника (найден попутно)

Полный прогон 37197322711 упал не в WebKit, а в «Pyodide в Node.js»: `pandas/mistakes#merge-right` — «ValueError:
putmask: output array is read-only» (то же отмечено в отчёте ci-speedup как «нестабильно»). Причина: валидатор
раздавал воркерам пула по одному **примеру**, и статья видела состояние, оставленное другими: после ячейки `arrow`
статьи `pandas/performance` (загружает pyarrow) `merge` в другой статье падает. С `--jobs 1` и `--jobs 2` пример
падал всегда, с 3–5 — в зависимости от того, как разошлись примеры. На сайте у страницы статьи свой воркер, поэтому
посетителей это не касалось. Теперь каждая статья выполняется в своём Python — как на сайте; результат одинаков
при любом числе воркеров и совпадает с `reference/browser.json`. Цена — задание идёт ~3,7 мин вместо ~45 с.

## Порог повторов (добавлено после ревью)

Каждая часть браузера пишет повторы в `browser-logs/retries-*.json`; задание `ci-ok` складывает их по прогону,
