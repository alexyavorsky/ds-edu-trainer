В прошлых уроках подклассы переопределяли `label`, и код вида `item.label()` давал для каждого класса свою
строку. У этого есть имя: **полиморфизм** (polymorphism) — один вызов, разное поведение у разных классов.
Главная польза полиморфизма в том, что код, который *вызывает* метод, не нужно менять, когда появляется новый
класс.

## Один вызов — разные классы

Касса предлагает несколько способов доставки. Каждый способ — свой класс со своим расчётом, но у всех есть
метод `cost(km)`. Код, который выбирает доставку, не проверяет классы — он просто вызывает `cost`:

<Demo id="delivery" title="Три доставки, один вызов" />

Без полиморфизма функция выглядела бы как цепочка `if isinstance(...) elif isinstance(...)`, и каждый новый
способ доставки требовал бы правки этой цепочки.

<Exercise id="cheapest" title="Самая дешёвая доставка">
Напишите функцию `cheapest(options, km)`: она возвращает тот способ доставки из списка `options`, у которого
`cost(km)` меньше всех. Функция не должна зависеть от того, какие классы в списке.

<Hint>`min(options, key=...)` с функцией, которая для способа доставки возвращает его `cost(km)`.</Hint>
</Exercise>

## Утиная типизация

Обратите внимание: классы доставки в демонстрации даже не связаны наследованием. Python не проверяет, от
какого класса объект, — ему достаточно, что у объекта есть нужный метод. Это называется **утиная типизация**
(duck typing): «если что-то ходит как утка и крякает как утка — это утка».

<Demo id="duck" title="Подарочный сертификат в чеке" />

Функции `receipt` нужны только `name` и `price`. Сертификат — не товар и не наследует от `Product`, но в чек
попадает так же.

<Exercise id="total" title="Сумма чего угодно">
Напишите функцию `total(items)`: сумма атрибутов `price` всех объектов списка — товаров, сертификатов,
услуг, чего угодно с атрибутом `price`.

<Hint>Достаточно `sum(item.price for item in items)` — без проверок класса.</Hint>
</Exercise>

<Mistake title="лишняя проверка класса">
Проверка `isinstance(item, Product)` в такой функции не защищает, а мешает: сертификат или услуга с ценой
будут молча пропущены, и сумма окажется меньше. Проверяйте класс, только когда поведение действительно
зависит от него.
</Mistake>

## `hasattr`: проверить, есть ли метод

Иногда нужно узнать заранее, умеет ли объект что-то. Встроенная `hasattr(объект, "имя")` возвращает `True`,
если у объекта есть атрибут или метод с таким именем:

<Quiz id="poly-quiz">
В кассу добавили класс `Taxi` с методом `cost(km)`. Что нужно изменить в функции `cheapest`?

- [x] ничего
- [ ] добавить `isinstance(option, Taxi)`
- [ ] сделать `Taxi` подклассом другого способа доставки

<Explain>`cheapest` вызывает только `cost(km)`, а у `Taxi` этот метод есть. Наследование тут не обязательно — достаточно утиной типизации. Так и выглядит полиморфизм: новый класс встраивается, а старый код не меняется.</Explain>
</Quiz>
